## 全局变量

### 1.0 什么是全局变量

Solidity 提供了一些内置的 全局变量（Global Variables），用于访问区块链状态、交易信息等数据。这些变量不需要额外声明，可以在智能合约中直接调用

### 2.0 主要全局变量分类

solidity 全部变量分类：

#### 2.1 区块信息（Block Information）

|变量|类型|作用|
|---|---|---|
|block.number|uint|当前区块编号|
|block.timestamp|uint|当前区块时间戳（秒级）|
|block.coinbase|address payable|当前出块矿工的地址|
|block.difficulty|uint|当前区块难度|
|block.gaslimit|uint|当前区块的gas|
|block.basefee| uint|EIP-1559 之后的基本交易费|

示例：获取当前区块号和时间戳

```sol
contract BlockInfo {
    function getBlockDetails() public view returns (uint, uint) {
        return (block.number, block.timestamp);
    }
}
```
#### 2.2 交易信息（Transaction Information）

|变量|类型|作用|
|---|--|--|
|tx.gasprice|uint|交易的gas价格
|tx.origin|adress|交易的发起者（外部账户地址）|

注意：tx.origin 可能导致安全漏洞，避免用于身份验证！ 示例：检查交易发起者 contract TxInfo { function getTxOrigin() public view returns (address) { return tx.origin; } }

#### 2.3 消息信息（Message Information）
|变量|类型|作用|
|---|--|--|
|msg.sender|address|当前调用合约的地址（可能是外部账户或其他合约）|
|msg.value|uint|当前交易发送的以太币数量（单位：wei）|
|msg.data|bytes|当前调用合约的输入数据|

示例：获取调用者地址和发送的 ETH 数量



```sol
contract MessageInfo {
    function getMessageDetails() public payable returns (address, uint) {
        return (msg.sender, msg.value);
    }
}
```
#### 2.4 以太坊环境信息(Ethereum Environment Information)

|变量|类型|作用|
|--|--|--|
|gasleft|uint| 当前剩余的gas|
|block.chainid|uint|当前链的ID(EIP-1344)|
|address(this)|address|当前合约的地址|
|this.balance|uint|当前合约的ETH余额|

示例：获取当前合约的地址和余额

```sol
contract ContractInfo {
    function getContractDetails() public view returns (address, uint) {
        return (address(this), address(this).balance);
    }
}
```

#### 2.5 this 关键字
this 关键字用于引用当前合约的实例，它可以用于：

1. 获取当前合于的的地址
2. 在合约内部调用自身的函数（但会创建新的交易）
3. 访问当前合约的balance, 示例：使用this 关键子

```sol
    contract ThisExample {
        function getContractAddress() public view returns (address) {
            return address(this);
        }

        function getContractBalance() public view returns (uint) {
            return address(this).balance;
        }
    }
```

注意事项：
* this 关键字调用合约自身的函数时，会触发新的交易，因此会消耗额外的 gas。
* this.balance 获取的是合约的 ETH 余额，而 msg.sender.balance 可以用于获取调用者的余额。

#### 2.6 其他特殊全局变量

|变量|类型|作用|
|---|---|--|
|abi.encode(...)|bytes|ABI 编码|
|abi.decode(...)|T| ABI 解码|
|keccak256(...)|bytes32| 计算Keccak-256哈希|
|sha256(...)| bytes32| 计算SHA-256 哈希值|
|repemd160(...)|byets20|计算RIPEMD-160哈希值|
|ecrecover(...)| address| 从签名中恢复公钥|
|addmod(x,y,m)|uint| 计算(x+ y)%m,避免溢出|
|mulmod(x,y,m)|uint|计算(x*y)%m,避免溢出|

示例：使用 keccak256 计算哈希值：

```sol
    contract HashExample {
        function getHash(string memory input) public pure returns (bytes32) {
            return keccak256(abi.encodePacked(input));
        }
    }
```

**总结**
Solidity 提供了许多 全局变量，可以访问 区块链状态、交易信息、消息信息等。
this 关键字可用于引用当前合约地址、余额或调用自身函数（会消耗额外 gas）。
数组、哈希、加密函数 也是 Solidity 重要的全局功能。
在开发合约时，应 正确使用全局变量，避免 安全隐患（如 tx.origin）。

**为什么 tx.origin 不安全？**
 
1. tx.origin 是 Solidity 内置全局变量，返回触发当前交易的 “原始外部账户地址”（即最终发起交易的人，而非直接调用合约的地址）。

2. 核心安全风险：钓鱼攻击（Phishing Attack）
tx.origin 的风险源于其 “穿透中间合约” 的特性，攻击者可构造恶意合约诱导用户触发交易，骗取用户权限或资产。

**攻击流程示例（以 “仅允许所有者转账” 的合约为例）：**

```sol
// 有漏洞的合约：用 tx.origin 验证所有者
contract VulnerableContract {
    address public owner;
    constructor() { owner = msg.sender; }

    // 漏洞点：用 tx.origin 判断所有者
    function transferFunds(address to, uint amount) public {
        require(tx.origin == owner, "Only owner can transfer"); // 危险！
        payable(to).transfer(amount);
    }
}

// 攻击者的恶意合约
contract AttackContract {
    VulnerableContract public immutable targetContract;

    constructor(address _targetContract) {
        targetContract = VulnerableContract(_targetContract);
    }

    // 诱导所有者调用此函数（比如伪装成“领取奖励”）
    function fakeClaimReward() public {
        // 当所有者调用此函数时，tx.origin = 所有者地址
        targetContract.transferFunds(msg.sender, 100 ether); // 攻击者地址接收资金
    }
}
```
攻击步骤：
* 攻击者部署 AttackContract，传入受害者的 VulnerableContract 地址；
* 攻击者诱导受害者（VulnerableContract 的所有者）调用 fakeClaimReward()（比如发钓鱼链接，说 “点击领 ETH”）；
* 受害者调用后，tx.origin = 受害者地址（原始交易发起者），满足 tx.origin == owner 的校验；
* 恶意合约自动调用 transferFunds，将受害者的资金转到攻击者地址。

如何使用 block.timestamp 生成随机数？


适用场景（低安全需求）
生成非敏感的序号（如订单号、活动参与编号）；
简单演示场景（如教学 demo、无奖励的抽奖演示）；
对随机性要求低、无经济利益关联的功能（如随机展示某条内容）。
2. 绝对不适用场景（高安全需求）
彩票、赌博、NFT 盲盒等涉及资产分配的场景；
随机分配稀缺资源（如限量 NFT、空投资格）；
任何需要 “不可预测、不可篡改” 随机性的场景。
3. 核心局限性
矿工可影响：矿工打包区块时，可微调 block.timestamp 和 block.number，存在微小操纵空间；
可预测性：若攻击者提前获取所有输入参数（如 msg.sender、seed、block.number 预估），可提前计算出随机数；
取模偏差：当 baseRandom 的最大值不是 (max - min + 1) 的整数倍时，范围边缘的数值概率会略低（如 baseRandom 最大为 101，%100 后 0 和 1 的概率是 2/102，其他是 1/102）。
五、高安全场景的替代方案
若需 “绝对安全、可验证” 的随机数（如彩票、盲盒），必须使用 链下验证的随机数方案，主流方案如下：
1. Chainlink VRF（推荐）
原理：去中心化预言机提供 “可验证随机函数”，生成随机数后会附带一个 “证明”，链上可验证该随机数未被篡改；
优势：安全、去中心化、可验证，是行业标准方案；
用法：集成 Chainlink VRF 合约，调用其 requestRandomWords 函数获取随机数。
2. 其他预言机方案
Band Protocol、API3 等预言机也提供类似 VRF 的随机数服务，原理与 Chainlink 类似。
3. 链下签名方案
由可信第三方（如项目方）生成随机数并签名，链上验证签名有效性后使用；
缺点：中心化，依赖第三方诚信，适合对去中心化要求不高的场景。


gasleft() 在合约执行过程中会如何变化？

1. 交易发起时，-》gesleft()->gasLimit:

用户发起交易时，会指定 gasLimit（如 50000）和 gasPrice（Gas 的单价）。此时交易尚未执行任何合约指令，剩余 Gas 等于设定的最大 Gas 限制：gasleft() = gasLimit（例：50000）。

2.  阶段 2：执行合约指令时 → 逐步递减
    交易被矿工打包后，EVM 开始执行合约函数，每执行一条指令，gasleft() 就会减去该指令对应的 Gas 消耗，持续递减。
常见指令的 Gas 消耗示例（仅作参考）：

* 简单运算（ADD/SUB/LT）：2~3 Gas；
* 读取状态变量（SLOAD）：800 Gas；
* 存储状态变量（SSTORE，首次存储非零值）：22100 Gas；
* 转账（transfer/call）：至少 2300 Gas（基础转账消耗）+ 接收合约的执行消耗。

3. 函数调用-> 大幅递减（外部调用）
若合约函数中包含 内部函数调用 或 外部合约调用，gasleft() 会有不同变化：
 * 内部函数调用（同一合约内）：仅消耗指令本身的 Gas，gasleft() 平缓递减；

 * 外部合约调用（跨合约）：除了调用指令的 Gas，还需额外消耗 “跨合约通信” 的基础 Gas（约 3000 Gas），且外部合约执行的所有指令都会消耗当前交易的 Gas，导致 gasleft() 大幅下降。


4. 阶段 4：交易结束时 → 剩余 Gas 返还或耗尽

交易执行到末尾（函数执行完成 / 触发 return/revert），gasleft() 有两种结局：

* 正常结束：gasleft() > 0，剩余未使用的 Gas 会按 gasPrice 折算成 ETH 返还给交易发起者（不浪费）；

* Gas 耗尽：gasleft() = 0，触发 Out-of-Gas 异常，交易直接回滚（所有状态变更失效，比如转账、存储修改都作废），且已消耗的 Gas 不返还（矿工已执行指令，需支付手续费）。
